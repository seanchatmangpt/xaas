# W333 — ash_onetime `:store_invariant` diagnosis (OS-12 operator decision memo)

Subject: xaas @ feat/playwright-surface (d1db2b03), ash_onetime hex 1.2.3 (mix.lock:22).
Probe: real `mix run` under MIX_ENV=test, pinned asdf toolchain, 2026-10-06.
All findings below are from executed probes against the real sandboxed Postgres, not source
inspection alone.

## 1. Mechanism (typed, with file:line)

The failing claim INSERT (real probe, MIX_ENV=test):

```
{:pg_error, "ERROR 42703 (undefined_column) column \"logical_partition\" of relation
 \"ash_onetime_nonce_claims\" does not exist", :undefined_column}
```

Chain:
1. `EnforceSingleRevoke.change/3` registers `before_action` (`lib/xaas/accounts/token/enforce_single_revoke.ex:21`)
   → runs a real `Ash.create` on `RevokeNonce` `:claim` (enforce_single_revoke.ex:27-29).
2. `RevokeNonce` hosts the `onetime protect :claim` block
   (`lib/xaas/accounts/token/revoke_nonce.ex:41-48`; strategy `:one_time_nonce`, scope
   `{:static, "revoke_token"}`, key `{:verified, :token, RevokeVerifier}`).
3. `AshOnetime.Admission.reserve/3` → `AshOnetime.Store` → `AshOnetime.Store.Postgres.claim/2`
   (`deps/ash_onetime/lib/ash_onetime/admission.ex:60-96`).
4. `Store.Postgres.insert_claim/3` issues an INSERT naming `logical_partition`
   (`deps/ash_onetime/lib/ash_onetime/store/postgres.ex:492-506`).
5. Any `Postgrex.Error` maps to `Result.failure(:store_invariant, :sent, :rolled_back)`
   (postgres.ex:1250-1252) → generic `decide/5` → `Admission.store_error/1`
   (admission.ex:1037-1039) → `AshOnetime.Error code: :store_invariant,
   message: "authoritative admission store failed"`.

Root cause: **install-migration drift, not a sandbox limitation.** Xaas' hand-written
`priv/repo/migrations/20260820213658_install_ash_onetime.exs` is a pre-1.1 template:
- nonce table DDL (lines 63-82) declares no `logical_partition` column;
- idempotency table DDL (lines 17-43) declares no `logical_partition`;
- `ash_onetime_response_payloads` (lines 107-115) declares
  `PRIMARY KEY (partition_date, claim_id)` with no `logical_partition`.

The pinned ash_onetime 1.2.3 store requires `logical_partition` on all three tables
(`priv/templates/migrations/install.exs:19,68,114` in the vendored package; canonical PK
`(logical_partition, partition_date, claim_id)` at template line 119). Upstream doc:
`deps/ash_onetime/documentation/upgrading.md` §v1.1.0 — fresh installs include the column;
existing installs must run `mix ash_onetime.gen.logical_partitions --repo MyApp.Repo` +
`mix ecto.migrate`. Neither happened in xaas. Confirmed missing in both `xaas_test`
(probe) and `xaas_dev` (direct `psql information_schema` check: columns are
id, operation_hash, scope_hash, key_hash, issued_at, expires_at, verifier_id, admitted_at,
retain_until, inserted_at — no `logical_partition` in either DB.

**This is not test-only**: dev DB has the same stale schema, so `:revoke_token` is
BLOCKED in every environment, not just sandboxed tests.

## 2. Minimal lawful fix (consumer-side, no library change)

Run the library's own sanctioned generator + migrate (both dev and test DBs):

```
PATH=$HOME/.asdf/shims:$PATH mix ash_onetime.gen.logical_partitions --repo Xaas.Repo
PATH=$HOME/.asdf/shims:$PATH MIX_ENV=test mix ecto.migrate
```

(or hand-add one additive migration `ALTER TABLE ... ADD COLUMN logical_partition text
NOT NULL DEFAULT 'global'` to all three ash_onetime tables per
`deps/ash_onetime/priv/templates/migrations/logical_partitions.exs`). This adds one
migration file to the xaas tree — consumer-side, generated by the pinned library's
generator (not hand-written DDL), no ash_onetime change. Closure-eligible as an additive
migration, same class as any schema addition.

Then verify:
```
MIX_ENV=test mix test test/xaas/accounts/token_revocation_test.exs
```
and expect `:revoke_token` to pass on first call; second call with the same token string
must fail with `:nonce_already_used`.

Optional preflight: `mix ash_onetime.doctor --live` — v1.2.0 added exactly this check
(schema-currency vs. the running package) and names
"upgrade-package-without-running-migrations" as a named failure instead of a cryptic
`:store_invariant` (upgrading.md §v1.2.0).

## 3. Classification

**(a)-adjacent: consumer-side schema migration, not a library change, not by-design.**
The invariant is correct; the store is behaving lawfully. What is stale is xaas' own
install migration (pre-1.1 DDL against a 1.2.3 package). Neither pure test-support fixture
((a) as stated) nor ash_onetime change (b) nor by-design (c). The fix is one additive
generated migration in xaas/priv/repo/migrations — operator-gated only because OS-12
itself is operator-gated; the library is untouched.

Optionally pair with the `ash_onetime.doctor --live` preflight in CI so this drift class
never resurfaces as a cryptic `:store_invariant` (typed guard, per the
failure→permanent-guard discipline).

## 4. jti PK collision (re-stated, operator design question)

`Xaas.Accounts.Token`'s `tokens` table (`lib/xaas/accounts/token.ex:23-24`,
attributes at 117-124):
- `attribute :jti, :string, primary_key?(true), allow_nil?(false), sensitive?(true)` (lines 117-122)

Under `store_all_tokens?(true)` (the test's disclosed premise,
`test/xaas/accounts/token_revocation_test.exs:44-47`):
- Minting a JWT pre-stores a `tokens` row with `purpose` = the mint purpose, PK = the
  token's `jti`.
- `:revoke_token` (`token.ex:53-76`) via `AshAuthentication.TokenResource.RevokeTokenChange`
  inserts the revocation row with the SAME `jti` as PK
  (AshAuthentication's RevokeTokenChange semantics: the revocation row reuses the token's
  jti so `IsRevoked` finds it by jti lookup).
- Result: PK conflict — the revocation row cannot coexist with the stored-token row.
  The test works around it by deleting the pre-stored row inside the sandboxed
  transaction before `:revoke_jti` (`clear_stored_token_row!/1`,
  token_revocation_test.exs:49-56).

Note: `Xaas.Accounts.Token` does not set `store_all_tokens?` in its DSL (not found in
token.ex) — the pre-stored row comes from AshAuthentication's token storage during sign-in
strategy token storage, not from an explicit `store_all_tokens?(true)` DSL pin in xaas;
the collision is real either way: one row per jti in a table whose PK is jti can hold
either the stored token OR the revocation marker, never both. Upstream design question:
AshAuthentication's revocation model assumes either (i) `store_all_tokens?(false)` (no
pre-stored row; the revocation row is the only row with that jti) or (ii) a
revocation model where revocation is an attribute/update of the stored row, not a second
row. With a jti PK there is no room for both. The operator decision: keep the workaround
(delete-then-revoke, sandbox-real but semantically a mutation AshAuthentication doesn't
 sanction), or change the table shape (composite PK / revocation-by-update) — a
consumer-side design change, operator-gated.
