## (3) Implementation plan for the next lane (minutes-scale execution)

Preconditions: `git status --porcelain | grep billing` → empty (clean tree),
and w905's sequencing note (SPEC-06 guard landed) holds.

**Step 1 — production change, per action (start with #4
ApprovalSlaCreditApply, the w905-named money-mover):**

1. Read the change module (e.g.
   `lib/xaas/billing/changes/approval_sla_credit_apply_approve.ex`). Classify
   its `after_action` body:
   - **Atomicizable** (single `Ash.create` Ledger Transfer + one
     changeset-attribute set, all expressible as `atomic/3` or a change whose
     `atomic/3` callback Ash can batch): convert to `atomic/3` (or
     `batch_callbacks`/`atomic_update` where the write is a plain column set:
     `Ash.Changeset.atomic_update(record_field, expr(...))`), move the Ledger
     Transfer creation into `after_action` retained ONLY if the whole body
     can run inside the parent transaction with no Elixir-side reads of
     post-commit state — otherwise keep `after_action` and disclose.
   - **Non-atomicizable**: leave `after_action/2` in place, add a one-line
     disclosure in the module moduledoc: `## Atomicity disclosure: after_action
     retained; <reason>`.
2. Where converted, drop `require_atomic?(false)` if the action is now fully
   atomic; keep it if any non-atomic hook remains (Ash errors otherwise at
   compile-time verification).
3. Remove `require_atomic?(false)` ONLY after `mix compile` is green.

compile gate: `mix compile` (real tail in receipt).

**Step 2 — Chicago court** (new file
`test/xaas/billing/atomic_retrofit_court_test.exs`, real Postgres sandbox,
real actions, no mocks):

- (a) **Atomic-quantity block** (w905 lens-d class): approve a credit; assert
  the real `Xaas.Ledger.Transfer` row exists with real amounts; a failure
  injected by pointing the credit at a nonexistent account id rolls back the
  approval too — the record is NOT "approved but never credited".
- (b) **Concurrency block**: two simultaneous `:approve` on the same record
  (real `Task.async` pair over the sandbox in manual mode, checked out in
  each task): exactly one Transfer minted, exactly one approval; second gets
  typed refusal or no-op, never a double credit. Extends the W746-class
  `filter(expr(is_nil(approved_by)))` DB guard already on Transfer.
- (c) **Action-atomicity probe**: converted actions run without
  `require_atomic?(false)` bypass (compile-level, asserted implicitly by the
  action definitions; document in court moduledoc).

Block (b) design detail: use `Ecto.Adapters.SQL.Sandbox.start_owner!/2` per
task; assert `Repo.aggregate(Transfer, :count)` == 1 after the pair.
