A2A caller's real identity to the actor it asserted); current mitigation: documentation

## This cycle's concrete charter

1. **RCA fix**: add a real, lightweight workflow-serialization discipline for this repo
   — a lockfile-based guard (e.g. `.claude/workflow.lock` with PID + timestamp) that a
   `Workflow` script's first agent checks/writes before doing concurrent `mix compile`
   work, so future sessions don't reproduce this session's build-lock contention. Keep
   it simple: a real file-based mutex, not a new service.
2. **FMEA fix (primary)**: build a real, minimal binding between an A2A/MCP caller's
   actual authenticated credential and the actor it may assert. Given this repo's one
   real auth primitive is the shared `INTERNAL_API_TOKEN` (per
   `ResolveOrgActor`'s own disclosed design), the smallest real improvement is: a
   real, persisted `Xaas.Library.PersonaGrant` (or similarly named) resource mapping a
   caller-scoped credential to an allow-list of user ids it may act as, checked by
   `NextReadUserAgent.resolve_actor/1` before threading the actor through — turning
   silent impersonation into an explicit, auditable, denyable grant. If a full grant
   resource is too large for one cycle, land the audit-trail half first (log every
   `as:<user_id>` resolution to a real `Xaas.Operations.AuditLogEntry` row) and name the
   grant-enforcement half as carried-forward, explicitly, in the results doc below —
   do not claim the full fix if only the audit half lands.
3. **Verification via avatars**: use the real MCP (`/mcp`) and A2A (`/a2a`) surfaces to
   simulate at least 3 distinct Next Read personas (e.g. a real student actor, a guest/
   unauthenticated actor, and an actor attempting an unauthorized impersonation) as real
   Chicago-style tests — real HTTP/GenServer calls against the real Ash-backed app, no
   mocking of MCP/A2A internals — proving the new binding actually denies the
   impersonation avatar while the legitimate avatars still work.
